# 项目使用说明与功能地图

更新：2026-10-30。本文回答四个问题：**打开后怎么用、功能在哪里、每个功能有什么用、哪些可以删。**
代码和接口以当前 `main` 分支（Alembic head `f6a2c91d4e70`）为准。

---

## 0. 先用一句话理解这个项目

当前仓库里其实并存着两条产品线：

| 产品线 | 内容 | 代码来源 |
|---|---|---|
| **新主线：分类录入 + 知识库 + 数据分析** | 拍照/描述 → 分类建议 → 人工确认 → 知识条款核验 → 历史/统计/对标 → 云端知识包分发 | M1–M6 |
| **历史线：R0–R8 多模型研判平台** | 多模型分析、风险引擎、证据判定、追问、整改闭环、评测总览 | R0–R8 |

两条线共用登录、上传、任务、知识检索、复核和导出，但叙事不同。你感觉“功能繁杂”，主要来源就是这两条线同时出现在同一个导航和详情页里。**新主线本身并不大；历史线占了后端近一半代码和大量测试。**

## 1. 启动与访问

### 1.1 启动后端

```powershell
# 从仓库根目录
cd backend
$env:PROVIDER_MODE = 'mock'    # 无 Key 时明确使用 Mock
$env:AUTH_MODE = 'none'        # 仅本地开发；生产必须 jwt/token
.\.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8001
```

- 启动时会自动执行 Alembic 增量迁移；迁移失败会拒绝启动。
- 检查就绪：`http://127.0.0.1:8001/api/v1/ready`
- 接口文档：`http://127.0.0.1:8001/docs`
- 本地数据默认在 `backend/data/`：`app.db`、`uploads/`、`knowledge/`、`faiss/`、`langgraph.db`。

### 1.2 启动前端

```powershell
# 从仓库根目录
cd frontend
pnpm dev
# 若 pnpm 不可用：
# node node_modules/vite/bin/vite.js --host 127.0.0.1 --port 5173
```

打开 `http://127.0.0.1:5173`。Vite 已把 `/api` 和 `/uploads` 代理到 `http://localhost:8001`。

### 1.3 三种认证方式

| 模式 | 用途 | 登录方式 |
|---|---|---|
| `none` | 本地开发/演示 | 无需登录，所有管理按钮可见 |
| `token` | 旧部署兼容 | 静态 Bearer 凭证 |
| `jwt` | 真实角色与审计 | `/login` 登录；用户由 CLI 创建 |

JWT 首次使用：

```powershell
cd backend
.\.venv\Scripts\python.exe -m app.cli.create_user --username admin --role admin
```

角色：

- `inspector`：现场提交、保存人工分类、提交整改照片；可查知识/历史。
- `reviewer`：复核分类和研判、批准/拒绝、整改状态流转、查看管理分析。
- `admin`：以上全部 + 知识库/来源/知识包/用户管理。

`none`/`token` 模式没有个人身份审计，不能替代 JWT 的角色隔离。

## 2. 页面地图：打开后每个入口在哪里

| 路由 | 导航名称 | 谁能看见 | 一句话作用 |
|---|---|---|---|
| `/` | 现场研判 | 所有人 | 新建分类记录或纯人工记录，查看当前结果 |
| `/history` | 历史记录 | 所有人 | 查历史、筛选、批量导入案例 |
| `/analytics` | 管理分析 | reviewer/admin | 已确认记录的分布、地图、整改对标、趋势提示 |

| `/assessments/:id` | — | 所有人 | 单条记录的详情、复核、整改、导出 |
| `/login` | — | jwt 模式 | 登录 |

导航定义在 `frontend/src/App.vue`，路由定义在 `frontend/src/router/index.ts`。

## 3. 完整业务流程（照着走一遍）

下面每条都按“页面操作 → 后端接口 → 页面上应该看到什么”说明。

### 流程 A：现场分类录入（新主线核心）

1. 打开 `/`，选择 **AI 分类助手**。
2. 上传 1–3 张现场照片，填写情况描述（例如“3 栋 2 单元楼道堆满纸箱，挡住疏散通道”）。
3. 点 **生成分类建议** → 后端 `POST /api/v1/assessments`（`mode=classification`）创建记录并执行分类。
4. 结果区出现 AI 建议类别/标签、参考条款、Mock 标识。Mock 只用于演示，不代表真实识别质量。
5. 点 **采用建议填写**只是填入表单，不会保存。确认最终类别、标签、可选风险等级和备注后，点 **保存人工录入** → `POST /api/v1/assessments/{id}/classification`。
6. 记录进入“待审核”。reviewer/admin 打开详情，在“人工复核”里 **批准并定稿**（或填写意见拒绝）→ `POST /api/v1/assessments/{id}/confirm`。
7. 已定稿记录在 `/history` 可见，详情可导出 Markdown；风险等级没填就显示“未分级”，不会默认中风险。

**判断是否成功**：详情状态从“需要人工复核”变为“已确认”，历史列表出现该记录，导出内容含人工类别。

### 流程 B：仅人工录入（不调用模型）

1. `/` 选择 **仅人工录入**。
2. 填描述；可在“位置与来源”里填地址、区划、设施、场景、事件时间、数据来源，也可完全留空。
3. 点 **创建人工记录** → `POST /assessments`（`mode=manual`）。不调用模型、不做检索。
4. 保存人工分类后，同样走 reviewer/admin 审核。

经纬度可整体留空；填写时必须成对并提供坐标系。事件时间与录入时间分开保存。

### 流程 C：知识库发布与检索（新主线核心）

1. `/knowledge` → 展开 **上传知识文档**。
2. 填写标题、**可定位的 HTTP(S) 来源**、版本标识、行业目录、适用范围，选择 PDF/Word/Markdown/文本。
3. **保存待审核版本** → `POST /knowledge/documents`。文档此时是未审核，不进检索。
4. 点 **查看版本** → 填审核意见、勾选“已核对来源/版本/原文/范围” → **审核并发布** → `POST /knowledge/documents/{id}/review`。
5. 在顶部选择行业 + 关键词 → **检索已审核条款** → `GET /knowledge/search`。结果只含已发布且指纹与正文一致的条款。
6. 更新原文：在详情点 **上传此文档的新版本**。旧版本会标记“已被新版本替代”，旧引用和正文不变。
7. 索引异常时点 **重新构建索引**。

**规则**：发布必须来源可定位、版本非占位、适用范围非空、非演示资料；否则 422。没有结果时明确提示“未找到已审核的有效条款”。

### 流程 D：权威来源更新提醒（可选）

1. `/knowledge` 的 **权威来源更新提醒** 中填名称、HTTP(S) 链接、行业 → **添加来源**。
2. 点 **检查** → `POST /knowledge/sources/{id}/check`。第一次成功检查建立基线，不提醒。
3. 内容变化后该来源显示 **发现变化 / 待处理**；点 **确认已阅** 清除待处理。
4. 不可达或 HTTP 错误显示 **检查失败** 和错误原因。
5. **检查不会自动生成或发布新知识版本**；仍要按流程 C 上传并人工审核。

### 流程 E：管理分析与同类对标（可选）

1. reviewer/admin 打开 `/analytics`。
2. 选择区划/类别/设施/场景/月份 → **应用筛选** → `GET /analytics/overview`。
3. 页面展示：已确认总数、未分级数、风险分布、区划/类别分布、月度趋势（零月份也列）、地图点位、导入案例“收集到的案例数”。
4. **同类整改对标**：选设施和/或场景 → 查询 → 展示样本量、筛选条件、来源、匹配方式和可比性，并可点 **查看** 下钻原记录。
5. **历史趋势提示**：点 **评估最新完整月份** → `POST /analytics/trend-alerts/refresh`；可对提示“确认关注”或“标记误报”，并填写处理备注。

**口径**：只统计人工已确认记录；时间优先事件时间，缺失时用录入时间；模拟数据不参与趋势；导入案例不并入已确认统计；地图底图需要联网。

### 流程 F：云端审核 → 本地知识包（可选）

适用场景：单组织有一个“云端/中心”实例负责审核，多个本地实例只消费审核结果。

1. 云端 `/knowledge` 管理员上传并审核发布知识版本。
2. 云端点 **导出知识包** → `GET /knowledge/pack/export`。包内只有每个系列最新已审核版本 + 清单 + 每篇 SHA256。
3. 本地 `/knowledge` 点 **导入知识包** 选 JSON → `POST /knowledge/pack/import`。
4. 导入先校验清单和指纹；成功显示导入/跳过/替代/失败计数，并显示本地包版本和最后同步时间。
5. 同系列旧版本转为“已被新版本替代”，旧正文和已有研判引用不变；篡改包返回 422。

### 流程 G：历史研判、追问、整改（历史线，可冻结）

- `/history` 查看旧记录；点 **查看** 进入详情。
- `needs_more_info` 记录可提交补充信息（追问）；`POST /assessments/{id}/followup`。
- 详情中的“整改”面板可上传整改后照片、AI 前后比对、人工确认/退回、状态流转。
- reviewer/admin 可对历史研判做“修订并定稿”。
- 这些是 R0–R8 的能力，新主线不依赖它们。

### 流程 H：评测总览（历史线，可冻结）

- `/evaluation` 展示 `docs/evaluation/` / `backend/data/eval/` 的旧评测产物。
- 当前是 Mock 报告，明确标注“不代表真实质量”。
- 它不是运营统计；管理分析在 `/analytics`。

### 流程 I：历史页批量导入案例（可选）

- admin 在 `/history` 展开 **批量导入案例（JSON）**，选择 JSON 文件 → `POST /assessments/import`。
- 每行需要 `source_ref`、`description`、`data_source`（`report/public_case/simulated`），可选位置字段。
- 相同（来源，外部编号）会跳过；失败行逐条列出。
- 导入记录状态是 `imported`，不进入 AI 研判、不算人工确认；它会出现在历史列表（状态“已导入”），但在统计中只计入“收集到的案例数”。

## 4. 功能清单：在哪、有什么用、建议保留吗

### 4.1 核心业务链（建议保留）

| 功能 | 页面/入口 | 后端接口 | 作用 | 删除后果 |
|---|---|---|---|---|
| 登录与角色 | `/login` | `/auth/token`、`/auth/me` | 区分 inspector/reviewer/admin | 无审计、谁都能改知识 |
| 现场提交/图片上传 | `/` | `POST /assessments` | 创建分类或人工记录 | 主流程不存在 |
| AI 分类建议 | `/` | 同上（classification） | 给出建议类别/标签，不自动定级 | 退化为纯人工 |
| 人工分类保存 | 详情/首页 | `POST /assessments/{id}/classification` | 保存最终类别/标签/可选等级 | 无法进入审核 |
| 复核/定稿 | 详情 | `POST /assessments/{id}/confirm` | reviewer/admin 最终确认 | 记录停留在待审 |
| 历史/详情/导出 | `/history`、`/assessments/:id` | `GET /assessments`、`/export` | 查询和交付 | 记录不可用 |
| 知识文档版本 | `/knowledge` | `/knowledge/documents*` | 上传、版本、审核、发布 | 无法维护条款 |
| 条款检索与引用 | `/knowledge`、详情 | `/knowledge/search` | 分类时引用已审核条款 | 分类缺少依据 |
| 引用快照 | 详情 | 证据随记录保存 | 新版本不覆盖旧引用 | 历史引用会漂移 |

### 4.2 业务增强（按试点需要保留）

| 功能 | 页面/入口 | 后端接口 | 作用 | 删除/隐藏建议 |
|---|---|---|---|---|
| 位置、区划、设施、场景、事件时间 | `/` 折叠区 | `POST /assessments` 表单字段 | 为统计/对标提供维度 | 不做分析可隐藏表单 |
| 批量导入案例 | `/history` 折叠区 | `POST /assessments/import` | 导入公开/模拟案例 | 不收集外部案例可隐藏 |

| 地图 | `/analytics` | 同上 `map_points` | 点位分布 | 不需要地理决策可去掉 Leaflet/地图卡片 |
| 同类整改对标 | `/analytics` | `/analytics/benchmarks` | 找其他地点整改经验 | 没有整改数据可隐藏 |

## 5. 功能依赖关系（删之前先看）

```text
页面
 ├─ /             → POST /assessments → classification / manual
 │                  → Assessment / AssessmentImage / AssessmentJob / IdempotencyKey
 ├─ /history      → GET /assessments、POST /assessments/import
 ├─ /assessments/:id
 │                  → classification 保存/复核/导出
 │                  → evidence 快照（依赖 knowledge search）
 │                  → 整改/追问（历史线）
 ├─ /knowledge
 │                  → 文档版本 → knowledge_documents
 │                  → 检索 → rag + 已审核文档
 │                  → 来源提醒 → knowledge_sources
 │                  → 知识包 → knowledge_pack_imports
 ├─ /analytics
 │                  → 已确认 Assessment + 位置字段
 │                  → trend_alerts
 └─ /evaluation    → 旧评测报告文件
```

**关键依赖**：

- 引用快照依赖知识库的“已审核 + 内容指纹”；删掉知识审核就不能保留可追溯引用。
- 管理分析依赖人工确认和位置字段；没有确认记录时页面只会是空状态（当前就是这样）。
- 知识包依赖知识版本与审核；没有云端/本地双实例，知识包就是多余功能。
- 趋势提示依赖至少 7 个月且每类 ≥10 条已确认记录；数据不足时只显示“资料不足”。

## 6. 选择性精简：三套方案

### 方案 A：试点最小（推荐先用这套验证业务）

保留页面：`/`、`/history`、`/assessments/:id`、`/knowledge`（只保留搜索 + 上传/审核 + 文档列表）。

| 保留 | 隐藏/移除 |
|---|---|
| 登录/角色、现场提交、分类建议、人工保存、复核、历史/导出 | `/analytics` 整页 |
| 知识上传/版本/审核/检索/引用快照 | 地图、对标、趋势 |
| 位置字段可留（不展示分析） | 来源提醒、知识包 |
| 历史记录只读 | 评测总览、追问、整改、双模型/风险引擎 |

效果：4 个主页面，导航只剩“现场研判 / 历史记录 / 知识库”；新业务闭环完整，历史数据仍可查。
适合：1 个试点单位、少量用户、先验证“分类+知识+复核”是否省时间。

### 方案 B：单组织完整（推荐正式试点）

保留 A 的全部 + `/analytics` + 位置/地图 + 来源提醒 + 知识包；隐藏 `/evaluation` 和旧研判的“追问/整改/多模型/风险引擎”等研究面板（历史详情只读）。

适合：有管理者看分布、有云端/本地两个部署点、有法规更新跟踪需求。

### 方案 C：全保留（当前状态）

适合：还要继续做模型质量研究、评测对比、历史研判兼容和整改闭环。

### 6.1 最快隐藏清单（只改前端，不动数据和接口）

如果只想先让界面变简单，按下面改即可，功能随时可恢复：

## 7. 删功能的安全顺序

不要一上来删数据库表或迁移。建议按风险从低到高：

1. **只隐藏导航/卡片**（最低风险）：改 `App.vue`、对应 view 的 `v-if`。接口和数据保留，随时可恢复。
2. **移除前端页面和路由**：删 view、router 条目、store 里的对应 action。后端仍兼容旧客户端。
3. **移除后端接口**：删 `routes.py` 中对应路由、schemas、service、测试；确认没有其他调用方。
4. **移除依赖/服务**：如 Leaflet、评测脚本、双模型服务；同步更新 `package.json`/`pyproject.toml` 和锁文件。
5. **数据库表**：**不要删历史迁移**；如需删表，新增一个可审阅迁移，并先备份。已有业务数据不要批量重写。
6. **更新测试与文档**：删除或改写对应测试，避免默认回归继续要求已删除功能。

建议先按第 1 步隐藏 1–2 周，观察是否真的没人使用，再进入第 2–4 步。

用默认 `backend/data/app.db` 启动时：

## 10. 选择精简前的检查清单

逐项回答，答“否”的功能就可以按第 7 节顺序隐藏：

- [ ] 有专人每月看地区/类别分布和趋势吗？否 → 隐藏 `/analytics`。
- [ ] 需要地图辅助定位吗？否 → 去掉地图卡片和 Leaflet。
- [ ] 需要按设施/场景找其他地点整改经验吗？否 → 隐藏对标。
- [ ] 有云端审核 + 本地消费的双部署吗？否 → 隐藏知识包。
- [ ] 有固定的权威法规页面需要跟踪变化吗？否 → 隐藏来源提醒。
- [ ] 需要管理整改照片和闭环状态吗？否 → 隐藏整改面板。
- [ ] 还需要 AI 追问、多模型比较、风险引擎和评测报告吗？否 → 冻结历史研究线。
- [ ] 首版真的需要 PostgreSQL 吗？否 → 只保留 SQLite，另一个仅保留兼容。
- [ ] 需要个人审计和三角色吗？是 → 保留 JWT；仅本地演示可短暂用 none。

如果一个功能连“谁在什么场景下用、用完得到什么”都说不清，它就不应该留在首版导航里。
