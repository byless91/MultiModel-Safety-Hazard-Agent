## 1. 总体目标与原则

**目标**：将当前"质量不错的演示原型"升级为"可部署、可运营、质量有自动化保障"的系统。差距不在功能，而在请求模型、认证体系、可观测性、工程化门禁四块基座。

**原则**：

1. 每个批次结束时系统必须处于可运行、可部署状态，不允许长期停在"改了一半"。
2. 不推倒重来：现有 guardrail / ensemble / 评测体系是资产，只加固不重写。
3. 优先做"投入小、杠杆大、不改变现有功能逻辑"的改动。
4. 所有改动按 `code-project-rule` 技能执行：前后代码展示 → 即时测试（测试入 `backend/tests/`，遵循 `test_*.py` 命名）→ 思路与反思。
5. 自本次改造起采用 conventional commits（`feat:` / `fix:` / `refactor:` …），每批次结束打 tag（`v0.2-b0` 等）。

## 3. 推进批次总览（v1.1：稳定性优先版）

> 排序原则：**每一步要么增加系统的"可验证性"，要么改变系统行为，绝不同时做两件事。** 安全网（CI）、眼睛（可观测性）、减脂（去重复）全部前移到动刀（异步化 / checkpointer）之前；迁移纪律（Alembic）前移到所有需要加表的批次之前。WP 编号是任务标识，不代表执行顺序；§4–§9 是工作包详情的主题分组。

| 批次 | 内容 | 工作包 | 预估 | 为什么在这个位置 |
|---|---|---|---|---|
| B0 | 安全网 + 速赢 | WP5.1（CI + 锁文件）、WP0.1–0.3 | 2–3 天 | CI 从原计划末位前移到第一位：此后每个改动都被自动回归兜底；速赢项在 CI 保护下逐个落地 |
| B1 | 眼睛 + 减脂（纯增量，零行为变化） | WP3.3（request id / 结构化日志 / 指标）、WP5.5（去重复） | 2–3 天 | 只加日志与指标、只合并重复代码，不改行为；让最高风险的 checkpointer 改造只面对一份代码，而非两份 200 行拷贝 |
| B2 | 迁移纪律 | WP4.1（Alembic） | 1 天 | B3/B4/B5 都要新增表（jobs / users / llm_calls），先立迁移纪律再加表，消灭 ensure_columns 双份维护漂移 |
| B3 | 动刀：异步化与状态恢复 | WP1.1 → WP1.2 → WP1.3 | 3–5 天 | 全计划最高风险，此时 CI、request id、单一代码路径、正式迁移全部就位；任务表（WP1.1）先行，checkpointer（WP1.2）失败可回退 sync 模式 |
| B4 | 认证与审计 | WP2.1–2.4 | 3–4 天 | 在稳定的请求模型上做；admin 角色是 B5 台账查询接口的前置 |
| B5 | LLM 工程化与 RAG | WP3.1、WP3.2、WP3.4 | 4–5 天 | 台账表走 Alembic、admin 接口走 B4 角色；WP3.4 基线重置必须在 B6 评测门禁启用前完成 |
| B6 | 部署与质量收尾 | WP4.2、WP5.2、WP5.3、WP5.4 | 3–4 天 | PG / Docker / 评测门禁 / 前端测试均为部署与收尾件，不影响前面批次的稳定性 |

依赖关系：B0 → B1 → B2 → B3 → B4 → B5 → B6，严格串行。WP3.3 中「`llm_calls` 表携带 request_id」的联动项随 WP3.2（B5）落地。

v1.0 → v1.1 的顺序变化：CI（WP5.1）从最后提前到最前；可观测（WP3.3）与去重（WP5.5）提前到动刀之前；Alembic（WP4.1）提前到所有加表批次之前。认证、LLM 工程化、PG/Docker/评测门禁的相对位置不变。

## 4. 速赢加固（WP0.1–0.3，批次 B0）

> 全部是小改动、不动架构，但每一项都消除一个已证实的缺陷。

### WP0.1 性能止血（A1、A4）

- `routes.py:563`：`create_assessment` 中 `run_workflow` 改为 `await run_in_threadpool(run_workflow, ...)`（或 `asyncio.to_thread`），消除事件循环阻塞。同模式的 `followup`、`confirm` 路径一并检查。
- `core/db.py`：SQLite 连接增加 `PRAGMA journal_mode=WAL`、`PRAGMA busy_timeout=5000`（通过 `event.listens_for(engine, "connect")`）。
- **验收**：新增测试 `backend/tests/test_concurrency.py`——并发 5 个研判请求期间 `/health` 在 1s 内响应；现有 33 个测试文件全部通过。
- **测试**：`test_concurrency.py`（`run_workflow` 用 Mock Provider + 人为 sleep 模拟慢调用）。

### WP0.2 输入与上传加固（B3、B4）

- 上传改为流式限量读（分块读入、累计超限即拒绝），三处：研判图片、整改照片、知识文档。
- 整改照片增加张数上限（复用 `max_images` 配置）。
- 图片入库前校验 magic bytes（JPEG/PNG/WebP 头），不信 `content_type`。
- `GET /assessments` 的 `limit` 做 `max(1, min(limit, 200))` 钳制；`status` 参数加枚举校验。
- `edits.risk_level` 校验为 1–4 整数，非法返回 422 而非 500。
- **验收**：`test_api.py` 扩展用例：负数 limit、非法 edits、超张数整改照片、伪造 content_type 的假图片均被 4xx 拒绝。

### WP0.3 静默失败显性化 + 工程卫生（D3、D4、B1 部分、E7、E8 部分）

- 三处静默吞噬补结构化日志：`langgraph_flow.py:118-139`（区分编程错误与模型故障，编程错误 re-raise）、`rag.py:219`、`routes.py:911-914`。
- `core/logging.py` 换 `RotatingFileHandler`；`OSError` 吞噬处降级到 stderr 输出。
- `main.py:55` token 比较改 `secrets.compare_digest`。
- `scripts/verify_e2e.mjs` 改为从 `frontend/node_modules` 解析 playwright（playwright-core 移入 frontend devDependencies），移除本机绝对路径。
- `backend/pyproject.toml`：`pytest` 移入 `[project.optional-dependencies].dev`；`frontend/pnpm-workspace.yaml` 清理占位文本、按需收紧 `dangerouslyAllowAllBuilds`。
- **验收**：`test_engineering.py` 扩展：断言 mock 降级路径写入日志记录；E2E 脚本在新 clone 环境可解析依赖（本地验证）。

## 5. 请求模型与状态恢复（WP1.1–1.3，批次 B3）

### WP1.1 研判任务化（A2）

**决策**：不引入 Celery/Redis。单节点部署下用「DB 任务表 + 进程内后台 worker」实现，与现有 SQLite 栈一致，零新增基础设施。

- 新增 `assessment_jobs` 表：`id / assessment_id / status(queued|running|succeeded|failed) / progress_step / error / created_at / updated_at`。
- `WORKFLOW_MODE=sync|async` 配置（默认先保持 `sync` 兼容现有测试与脚本；`async` 为目标模式）。
- async 模式：`POST /assessments` 立即返回 `202 + job_id`；进程内 worker（lifespan 启动的 asyncio 任务 + 线程池执行 `run_workflow`）消费队列，逐步更新 `progress_step`（分析中→检索中→研判中→证据校验→完成）。
- 新增 `GET /assessments/{id}/job` 查询接口；前端 store 改为提交后轮询（2s 间隔），研判页展示步骤进度。
- worker 崩溃恢复：启动时把 `queued/running` 超过阈值时间（如 10 分钟）的任务标记 `failed`。
- **验收**：`test_workflow_jobs.py`——async 模式下提交 3 个任务全部得到最终结果；kill worker 模拟后重启能清理僵尸任务；sync 模式下现有全部测试不受影响。
- **前端**：`stores/assessment.ts` 增加 `submitAndWait`（轮询）；`HomeView.vue` 提交后进入进度态。

### WP1.2 LangGraph checkpointer 与断点恢复（A3）

- 引入 `langgraph-checkpoint-sqlite`，`graph.compile(checkpointer=saver)`，`thread_id = assessment_id`。
- `info` 节点改为 `interrupt()` 挂起；`followup` 接口改为 `Command(resume=answer)` 从断点恢复，**不再重新调用视觉模型**。
- 人工复核（`awaiting_human_review`）同样走图状态挂起/恢复，`confirm` 结果回写图状态。
- **验收**：`test_langgraph_routing.py` 扩展——用 Mock Provider 计数器断言：追问恢复后 `analyze` 调用次数不增加；进程重启（新建 saver）后 thread 状态可恢复。
- **注意**：`workflow.py` 函数式回退路径保持行为一致（同步重跑可接受，但需标注降级语义）。

### WP1.3 幂等键（C2）

- `POST /assessments` 支持 `Idempotency-Key` 头：同 key 24h 内重复请求返回首次结果（幂等表或 assessment 表加列 + 唯一索引）。
- 整改 `compare` 接口加状态+时间窗去重：同状态 5 分钟内重复调用直接返回缓存结果，不再重复付费。
- **验收**：`test_idempotency.py`——同 key 双发只产生一条 assessment、Mock 调用计数不变。

## 6. 认证与审计可信（WP2.1–2.4，批次 B4）

### WP2.1 用户体系与 JWT（B1）

**决策**：不引入 fastapi-users 等重框架，用 `PyJWT + passlib[bcrypt]` 自建最小实现（用户表 + `/api/v1/auth/token` + 依赖注入 `get_current_user`）。

- `users` 表：`id / username / password_hash / role(admin|inspector|reviewer) / disabled`；CLI 脚本 `scripts/create_user.py` 建管理员。
- 中间件改为 JWT 校验（保留原 `API_BEARER_TOKEN` 作为服务间调用的兼容通道，标记 deprecated）。
- 角色规则：inspector 可提交研判/整改照片；reviewer 可确认复核/整改关闭；admin 可管理知识库与用户。
- `AUTH_MODE=none|token|jwt` 配置，`none` 仅限本地开发，生产文档标注必须 `jwt`。
- **验收**：`test_auth.py`——无 token 401；错误角色 403；密码哈希不出现在任何响应与日志。

### WP2.2 审计身份可信（B2）

- `ConfirmIn.reviewer`、`RectificationTransitionIn.by` 从请求体移除，服务端一律取认证身份；旧字段保留兼容读取但优先级低于 token 身份。
- 复核记录增加 `confirmed_by_id / confirmed_at` 外键化。
- **验收**：`test_human_review.py` 扩展——伪造 reviewer 字段不生效，记录中身份=token 身份。

### WP2.3 受保护的静态资源与前端登录态（B1、E3 部分）

- `/uploads` 改为鉴权路由流式返回（校验 JWT），或短期签名 URL（HMAC + 过期时间）；`StaticFiles` 挂载移除。
- 前端：登录页 + token 存储（pinia auth store）+ axios 请求拦截器注入 Authorization + 401 响应拦截器跳登录 + 路由守卫。
- **验收**：带 token 部署时前端全功能可用（含图片）；无 token 访问图片 401。

### WP2.4 基础限流（B1）

- 引入 `slowapi`：研判提交 5 次/分钟/用户，登录 10 次/分钟/IP（防爆破），知识库上传 admin 不限。
- **验收**：`test_rate_limit.py` 超限返回 429。

## 7. LLM 工程化与可观测性（WP3.1–3.4，批次 B1/B5）

### WP3.1 Provider 层加固（C1、C4、C6）

**决策**：不引入 LiteLLM。现有 provider 抽象质量尚可，在其上扩展，避免推倒重来。

- 共享 `httpx.Client` 连接池（provider 生命周期绑定，lifespan 关闭）。
- 重试改进：指数退避 + jitter、读取 `Retry-After`、429 与 5xx 区分策略。
- 捕获并落库 `usage`（prompt/completion tokens），请求/响应大小。
- JSON 解析失败不再静默：返回带 `parse_failed=True` 标记的结果，下游强制人工复核并在报告中标明"模型输出解析失败"（与"未检出隐患"可区分）。
- 修复 `last_retry_count` 并发污染：改为方法返回值传递而非实例属性。
- **验收**：`test_provider_abstraction.py` 扩展——usage 被记录；解析失败路径产出 `parse_failed` 标记且触发复核；并发调用 retry 计数互不干扰。

### WP3.2 LLM 调用台账与预算（C1、C2、C3）

- 新增 `llm_calls` 表：`assessment_id / provider / model / prompt_version / purpose(analyze|refine|compare|embed) / tokens_in / tokens_out / latency_ms / status / retry_count / parse_failed / created_at`。
- 每次调用（含失败）写入台账；`GET /api/v1/admin/llm-usage` 聚合查询（按天/模型/用途）。
- Prompt 移入 `backend/app/prompts/`（YAML + 版本号），调用时把 `prompt_version` 写入台账与 assessment 输出，评测结果可归因。
- 日预算配置 `DAILY_TOKEN_BUDGET`，超限后新研判直接转人工/排队，已有任务完成。
- 全局并发信号量（`MAX_CONCURRENT_LLM_CALLS`），线程池改为复用单例。
- **验收**：`test_llm_usage.py`——一次研判产生预期条数台账记录；超预算后新请求被拒或降级且日志可见。

### WP3.3 可观测性基座（D1、D2）

- `structlog` 结构化 JSON 日志 + `X-Request-ID` 中间件（响应头回传，日志全程携带，`llm_calls` 表同带 request_id）。
- `prometheus-fastapi-instrumentator` 暴露 `/metrics`：请求延迟/状态码、每 provider 成功率与重试率、研判端到端时长、队列深度。
- Langfuse/OTel 追踪**暂不引入**（决策点见 §11），先以 `llm_calls` 台账 + 结构化日志满足排障与成本分析。
- **验收**：`test_observability.py`——同一次请求的日志与台账记录 request_id 一致；`/metrics` 包含新增指标。

### WP3.4 RAG 修复与评测基线重置（C5、C7、E5、E6）

- `knowledge.py`：分块以「第X条」为边界（复用现有 `ARTICLE_RE`），每 chunk 携带自己的条文号，修复溯源错配；`write_records` 改原子写（tmp + replace）。
- `rag.py`：embedding 降级记录原因日志、加恢复探测（每次重建先试真实 API）；`rebuild` 加读写锁（`threading.RLock`），查询与重建不再竞态；FAISS 建索引前对真实 embedding 向量 L2 归一化。

## 11. 风险与决策点

| 编号 | 决策 | 推荐 | 备选 |
|---|---|---|---|
| DP-1 | 任务队列选型 | DB 任务表 + 进程内 worker（零新增设施，单节点够用） | 未来多副本时再上 ARQ/Redis |
| DP-2 | 是否上 PostgreSQL | Alembic 必做；PG 做成可选后端，多 worker 部署时强制 | 全量切 PG 会显著提高使用门槛 |
| DP-3 | LLM 网关 | 扩展现有 provider 层 + `llm_calls` 台账 | LiteLLM（会替换现有抽象，迁移成本大于收益） |
| DP-4 | LLM 追踪 | 暂不引入 Langfuse/OTel，台账+结构化日志先行 | 团队扩张、需要会话级回放时再引入 |
| DP-5 | 兼容策略 | `WORKFLOW_MODE`/`AUTH_MODE` 开关式灰度，旧路径保留至 B6 末 | 直接破坏式切换（现有脚本/测试会大量断裂，不推荐） |

**主要风险**：

1. WP1.2 checkpointer 改造动工作流核心，必须先有 WP1.1 的任务表兜底，改坏时可回退 sync 模式。
2. WP3.4 移除 mock 特判后演示链路置信度下降属**预期行为**（这正是修数据污染），需提前与使用方沟通，勿当 bug 回滚。
3. 阶段 2 前端登录态改造波及所有页面请求，需一次性完成，避免半认证状态。
