## 1. 目标与范围

将项目从“可以跑通演示链路”完善到“单节点可可靠运行、人工复核可追溯、评测结论有明确依据、全新环境能按文档部署”的版本。

本轮保留 FastAPI、Vue、LangGraph、SQLAlchemy、现有 Provider 和 RAG 架构。优先修复已有链路，不新增 Agent，不引入 Redis、Celery、LLM 网关或新的追踪平台。

本轮部署目标明确为**单副本、单 worker**，数据库可选 SQLite 或 PostgreSQL。PostgreSQL 支持不等于多 worker 支持；分布式 worker 和 PostgreSQL checkpointer 不作为本轮默认交付内容。

交付分为两个门槛：

- **工程验收**：下文所有必做工作包完成，离线回归、容器和 Mock E2E 通过。
- **真实场景验收**：真实图片与负样本标注就绪，真实模型评测已执行并满足实施前登记的质量目标。缺少数据或未执行真实模型时，明确记录为待验证，不得用 Mock 成绩替代。

遵循本次用户指定的 `C:/Users/34036/.codex/skills/code-project-rule/SKILL.md`。

该技能要求所有新增或修改的测试代码、数据、fixture、辅助代码位于**仓库根目录 `test/`**。这与仓库旧技能及旧计划中 `backend/tests/` 的约定不同，本轮以用户本次指定规则为准。

计划目录：


### 3.2 每个重大改动的流程

1. 重新定位当前实现和相关测试，保留需要展示的改动前片段。
2. 完成一个最小、可独立验证的行为改动。
3. 在 `test/` 编写聚焦回归测试，优先证明原缺陷并覆盖修复后的行为。
4. 立即运行该测试；失败时先定位、修复和复测，再进入下一项。
5. 在下一条可见回复中逐文件展示“改动前、改动后、测试、思路与取舍”；不展示测试代码内容。
6. 更新本计划的追踪表，记录实际命令、结果及尚未验证的环境。

一个阶段包含多个工作包时，仍按工作包逐项测试，不能合并成一次末尾验证。每阶段结束再运行相关历史回归；全部完成后运行全量回归。

文档修改本身进行引用、内容与 diff 检查，不为计划书制造无意义的运行时测试。自 2026-10-28 用户明确授权起，每完成一处重大改动，在验证通过后单独提交并推送到 `byless91/MultiModel-Safety-Hazard-Agent`，展示提交名称与哈希；不混入无关改动，不强制推送，不自动打标签或发布。

## 5. 工作包详情

### R0：测试入口与基线

**T01：接入根目录 test/**

- 涉及：pytest 路径配置、Vitest/TypeScript/ESLint 范围、CI 和测试说明。
- 新建独立测试初始化：导入应用前明确设置 Mock、测试数据库、知识库副本、上传和 checkpoint 路径；不加载真实 API Key，不继承任意生产 DATABASE_URL。
- 提供专用测试数据库参数供 PG CI 使用；保护逻辑拒绝已知真实库路径。不要通过复制历史 conftest 的硬编码路径重现旧问题。
- 新测试与历史测试可以分进程执行，避免历史 conftest 和模块级单例互相污染；CI 必须执行两组。
- 验收：`pytest --collect-only` 与 Vitest 用例发现均包含新旧测试；新增测试单独运行也有完整隔离；生产构建不打包 `test/`。

**T02：记录实施基线与故障复现**

- 将已证实的缺陷逐项转为对应工作包的测试设计，测试文件随修复提交到工作区；不一次性加入大量必然失败的测试后留下红色基线。
- 记录当前测试数量、评测集摘要、配置摘要和 git 修订标识；配置摘要不得包含 Key、密码或完整凭证。
- 验收：能区分历史通过项、已复现缺陷和待验证环境；后续测试数量变化有来源。

### R1：人工确认与审计保护

**T03：限制追问和确认的状态转换（P1）**

- 涉及：`backend/app/api/routes.py`、`assessment_io.py`、输入 schema。
- 追问只接受处于 `needs_more_info` 且没有活动任务的记录；对 confirmed、运行中、失败、已完成等不适用状态返回明确 409。sync/async 行为一致。
- 对已确认记录，本轮禁止普通追问直接重开；后续如确需重新研判，使用独立的新版本/关联记录流程，不复用原审批标记。
- 确认接口只能处理允许人工复核的终态；执行中的研判不能被抢先定稿。已经定稿的重复相同请求不得重复制造审计事件。
- 验收：inspector 不能改写已确认结论；非法请求不改变结论、复核人、确认标记、时间和审计内容。
- 聚焦测试：`test/backend/test_review_state_guards.py`。

**T04：保留人工修订历史并统一有效结论（P1/P2）**

- 涉及：确认接口、结果序列化、报告生成、必要的模型及 Alembic 迁移。
- 复核记录保留追加历史：操作、认证身份、时间、意见、修改前后值。AI 原始结果与人工最终结论可区分，不覆盖已有审计历史。
- 拒绝操作需要意见；对 edits 明确允许字段、类型和风险等级口径，非法值返回 422，避免任意字典造成不一致。
- 人工修改类别、等级或结论后，详情、摘要、工单和导出使用一致的有效结论；原风险规则计算保留为“AI/规则原始结果”，不能伪装成人工重算。
- 若新增持久字段，先增量迁移再改读写；测试新库及已有确认记录升级，保留兼容输出。
- 验收：批准、拒绝、修订均可追溯；重复提交和失败请求不丢失历史；UI/导出不会出现两套未经说明的最终等级。
- 聚焦测试：`test/backend/test_review_audit.py`、`test/backend/test_review_result_consistency.py`。

### R2：检索降级与逐项证据

**T05：使语料与查询始终处于同一 embedding 空间（P1）**

- 涉及：`backend/app/services/rag.py`、必要的缓存元信息。
- 明确 real/hash 模式与维度，降级时成对切换索引和查询；恢复时先完成候选索引与查询的兼容验证，再原子替换可用状态。
- 缓存键和元信息区分真实模型与 hash 空间，禁止混用。同维度也不能视为同一语义空间。
- 模型暂时失败不销毁可用缓存；日志记录模式变化和原因。检索质量下降必须可观测，不以静默假结果替代。
- 验收：缓存命中但查询失败、语料 embedding 失败、降级后恢复三条路径均不发生维度冲突；FAISS 与 NumPy 两路径覆盖；重建和查询并发不读到半成品。
- 聚焦测试：`test/backend/test_rag_embedding_recovery.py`。

**T06：具体隐患使用唯一 ID（P2）**

- 涉及：`ensemble/judge.py`、`workflow_nodes.py`、`evidence/judge.py`、必要的前端类型。
- finding_id 对每个具体隐患唯一，在同一结果的判定与回写过程中稳定；类别不再作为唯一键。
- 对齐 `location/locations` 读取规则，保留同类不同位置的发现；兼容历史结果展示，不重写历史报告来伪造证据。
- 验收：同类两位置、第一项证据不足而第二项充足时，逐项判定不会覆盖；顺序变化或证据回写也保持对应关系。
- 聚焦测试：`test/backend/test_finding_evidence_identity.py`。

### R3：任务恢复与状态一致性

**T07：让崩溃遗留任务可恢复到明确终态（P1）**

- 涉及：`job_runner.py`、任务模型、配置及必要迁移。
- 记录任务执行归属/执行代次，定期检查执行是否仍有效。快速重启遗留任务也必须在明确时限内被识别。
- 默认将无法确认完成情况的旧 running 标记失败并给出原因，避免自动重放已发生费用的调用；不因 queued 等待时间较长而把正常排队当作执行故障。
- 旧执行线程迟到时，不得覆盖已失败或新代次任务的结果。失败任务保留原研判/复核信息，重试作为明确新尝试处理。
- 验收：启动后短时间崩溃、10 分钟内重启、超时、正常长任务四种情况均有确定结果；恢复不需要再次重启；使用可控时钟测试，避免真实等待 10 分钟。
- 聚焦测试：`test/backend/test_job_recovery.py`。

**T08：原子入队和认领（P1）**

- assessment、幂等记录与初始 job 尽量在同一事务提交，避免出现 pending 研判却没有任务。
- job 认领采用条件更新/事务锁并校验影响行数；同一任务只有一个成功认领者。SQLite 与 PG 分别验证。
- 单 worker 为本轮受支持配置。部署入口及文档明确限制；增加原子认领不等于已解决共享 SQLite checkpointer、多副本上传和索引同步。
- 验收：两个并发认领者只有一个得到同一任务；任务创建事务失败不残留无任务研判；故障后不会出现重复结果回写。
- 聚焦测试：`test/backend/test_job_claiming.py`、`test/backend/test_job_enqueue_atomicity.py`。

**T09：事务性预留追问次数（P2）**

- 接受请求时原子检查状态、活动任务和剩余次数，并预留本次次数；worker 完成时不重复计数。
- 同一研判最多一个 queued/running 的追问，重复请求复用任务或明确返回冲突；定义失败后释放预留的规则，避免超限或永久耗尽。
- create 表单的 followup_answer、followup JSON、整改说明等真正进入模型的外部文本统一走输入校验，补齐旁路。
- 验收：并发发送五次追问不会排队五个任务；上限、失败回收、重复提交、注入文本在 sync/async 下符合一致规则。
- 聚焦测试：`test/backend/test_followup_reservations.py`、`test/backend/test_model_input_validation.py`。

### R4：模型并发与重复费用

**T10：统一真实模型并发入口（P2）**

- 涉及：`ensemble/analyzer.py`、Provider HTTP 入口和配置。
- 统一限制 analyze/refine/compare/embed 的真实 HTTP 并发，单模型不能绕过；等待、重试和异常释放规则明确，避免线程池与信号量嵌套死锁。
- 约束为单进程全局上限，不声称它是分布式限流或严格日预算预留。
- 验收：上限为 4 时，六个并发请求的实际 HTTP 活动数不超过 4；单/双模型、异常、重试和不同用途混合调用均覆盖。
- 聚焦测试：`test/backend/test_llm_concurrency_limit.py`；使用假 transport，不请求真实服务。

**T11：将前端提交接入现有幂等机制（P2）**

- 涉及：前端 assessment store、API 客户端和后端幂等响应。
- 每次新提交生成独立 key；同一次提交在网络超时后的重试复用 key，用户主动创建新研判才换 key。
- 同步失败不应诱导用户无意识重复付费；同 key 的 payload 不同应有明确冲突策略。async 重放保持稳定的 job/assessment 响应语义。
- 验收：响应丢失后重试只创建一个研判、一个初始任务；新提交不错误复用旧结果；页面给出可恢复的研判入口。
- 聚焦测试：`test/backend/test_idempotent_recovery.py`、`test/frontend/assessment-idempotency.spec.ts`。

**T13：修复 Compose 与健康检查（P1）**

- 两个 Compose 路径均验证启动顺序、端口、卷权限、反向代理、图片和数据持久化；CI 不只检查首页和 /health，还执行最小业务闭环。
