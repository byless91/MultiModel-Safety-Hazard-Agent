# 项目代码改写规则

适用于本仓库内一切代码改动任务（修改、重写、重构、修 bug、性能优化）。核心原则：**改动对用户可见、验证紧跟改动、测试代码只进文件不进聊天、重要判断附带说明。**

## 1. 在客户端界面展示改动前后代码

每完成一处代码改写，必须在回复中清晰展示该改动的前后对比：

- 用「改动前」「改动后」两个代码块，或一个 diff 风格代码块呈现；仅 1–3 行的小改动可只展示改动后片段并说明改了什么
- 每处改动标注 `文件路径:行号`，便于用户定位跳转
- 一处改动涉及多个文件时，逐文件分别展示
- 只展示被改动的片段，不要整文件粘贴

展示的目的是让用户**不需要打开文件就能审阅每一处改动**，所以宁可多一处展示，不可漏一处。

## 2. 每处大改动后立即测试

判断某处改动是否"值得测试"的标准：改动影响了运行逻辑、边界条件、数据流、接口行为、并发、异常处理或安全，就需要测试；纯文案、注释、格式调整不需要。

- 每完成一处这样的改动，立即编写并运行一次针对性测试验证可行；**不要把多个大改动攒到最后一起测**，否则出错时无法定位是哪一处引入的
- 测试失败时先修复、复测通过，再进入下一处改动；如实报告失败原因与修复过程，不得跳过或淡化失败的测试
- 报告测试时给出运行的命令与结论（通过/失败、关键输出摘要），但**不要把测试代码内容贴进聊天界面**——用户只需要知道测了什么、结果如何

## 3. 测试代码的位置

- 所有新写的测试代码放进项目已有的测试目录，遵循现有命名风格：后端测试放 `backend/tests/`（`test_*.py`，pytest）；不要在源码目录、仓库根目录或临时目录另起测试文件
- 前端如有测试，放 `frontend/` 下与其工具链对应的位置
- 新测试文件应与被测模块对应命名（如改 `backend/app/services/rag.py` 则写 `backend/tests/test_rag*.py` 或扩展已有的同名测试），优先扩展现有测试文件而不是重复新建

## 4. 思路与反思

每处较大改动完成后，在回复中用简短段落说明：

- **思路**：为什么这样改、方案上的取舍（为什么选这个方案而不是显而易见的替代方案）
- **反思**（可选）：改动或测试过程中暴露的问题、意外现象
- **改进思路**（可选）：后续值得继续优化的方向

「反思」与「改进思路」是可选的：没有值得写的内容，或改进点不符合本项目实际情况时，直接省略，不要为了凑格式硬写。
